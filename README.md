# Yoyo

Маркетплейс аренды вещей между людьми: от PS5 на выходные до дрели на один раз.

- Спецификация: [`docs/superpowers/specs/2026-11-03-yoyo-design.md`](docs/superpowers/specs/2026-11-03-yoyo-design.md)
- Дизайн-система: [`DESIGN.md`](DESIGN.md)
- Планы: [`docs/superpowers/plans/`](docs/superpowers/plans/)

## Структура

| Папка | Что внутри |
|-------|-----------|
| `apps/api` | API на NestJS + Prisma (PostgreSQL), все маршруты под `/api/v1` |
| `apps/web` | Сайт на Next.js |
| `packages/shared` | Общие для сайта и API константы, типы и схемы |

## Локальный запуск

Нужны: Node 24+ (на этом Mac стоит 26), pnpm 12, Homebrew.

1. Установить и запустить базу данных и ловушку для писем:
   ```bash
   brew install postgresql@17 mailpit
   brew services start postgresql@17
   brew services start mailpit
   ```
   PostgreSQL 17 из Homebrew не добавляет свои команды в `PATH`. Чтобы пользоваться `psql` и `createdb` напрямую, добавьте в `~/.zshrc`:
   ```bash
   export PATH="/opt/homebrew/opt/postgresql@17/bin:$PATH"
   ```
2. Создать локальную роль `yoyo` (пароль `yoyo`, только для разработки) и базы для разработки и тестов:
   ```bash
   psql -d postgres -c "CREATE ROLE yoyo LOGIN PASSWORD 'yoyo' CREATEDB;"
   createdb -O yoyo yoyo_dev
   createdb -O yoyo yoyo_test
   ```
   Право `CREATEDB` нужно Prisma: при `migrate dev` она создаёт временную «теневую» базу.
3. Поставить зависимости, создать файл настроек API, применить миграции и заполнить настройки по умолчанию:
   ```bash
   pnpm install
   cp apps/api/.env.example apps/api/.env
   pnpm --filter @yoyo/api db:migrate
   pnpm --filter @yoyo/api db:seed
   ```
   API не запустится без `JWT_SECRET` (не короче 32 символов). В `.env.example` он уже есть. Если `apps/api/.env` создан раньше, допишите строку из `.env.example` или свою, например из `openssl rand -base64 32`.
4. Запустить API:
   ```bash
   pnpm --filter @yoyo/api dev
   ```
   Проверка: <http://localhost:4000/api/v1/health> отвечает `{"status":"ok","db":"up",…}`. Документация API (Swagger, только не в production): <http://localhost:4000/api/docs>.

После изменения API обновите описание и типизированный клиент:

```bash
pnpm --filter @yoyo/api openapi:emit
pnpm --filter @yoyo/api-client generate
```

Письма, которые отправляет сайт при локальной разработке, не уходят наружу. Они видны в Mailpit: <http://localhost:8025>.

## Развёртывание

Всё бесплатно: база данных в **Neon**, API в Docker на **Render**, сайт на **Vercel**. Сервисы следят за веткой `main` и сами выкатывают каждое изменение.

**Работает сейчас:**

| Что | Адрес |
|-----|-------|
| Сайт | <https://yoyo-rent.vercel.app> (`/lv`, `/ru`) |
| API | <https://yoyo-api.onrender.com/api/v1/health> |

Проект Vercel: `yoyo-rent`. Сервис Render: `yoyo-api` (Blueprint `yoyo`, Frankfurt). База Neon: проект `yoyo` (Frankfurt, Postgres 17).

Первую настройку делает владелец пошаговым мастером:

```bash
./scripts/setup-deploy.sh
```

Мастер открывает нужные страницы, говорит, что нажимать, и сохраняет адреса и строку подключения **только на этом компьютере** в `.env.deploy` (файл в git не попадает).

| Где | Переменная | Значение |
|-----|-----------|----------|
| Render (API) | `DATABASE_URL` | строка подключения Neon (прямая, без pooling) |
| Render (API) | `WEB_ORIGIN` | адрес сайта: `https://yoyo.rent` (в production только `https://`) |
| Render (API) | `NODE_ENV` | `production` (задано в `render.yaml`) |

Шрифты, домен, почтовый сервис и хостинг меняются через эти настройки и `apps/web/src/styles/fonts.ts`, без переделки кода.

### Свой домен https://yoyo.rent

Сайт живёт на `https://yoyo.rent`. Старые адреса из `LEGACY_HOSTS` (например, `yoyo-rent.vercel.app`) навсегда (308) перенаправляются туда же, с тем же путём и параметрами. Правило собирает `apps/web/src/lib/legacy-redirects.ts`. `SITE_ORIGIN` и `LEGACY_HOSTS` читаются **при сборке**: после их изменения нужен новый деплой. Пока хотя бы одна из них не задана, перенаправлений нет, поэтому preview-деплои и локальная разработка не меняются.

`WEB_ORIGIN` на Render определяет CORS, проверку `Origin`, ссылки в письмах, `redirect_uri` для Google и адрес возврата после входа. Поэтому переключаться нужно в таком порядке:

1. **Google.** В OAuth-клиенте добавьте Authorized redirect URI `https://yoyo.rent/api/v1/auth/google/callback`. Старый адрес пока не удаляйте.
2. **Vercel.** Подключите домен `yoyo.rent`, задайте для Production `PROXY_SECRET`, `SITE_ORIGIN=https://yoyo.rent` и `LEGACY_HOSTS=yoyo-rent.vercel.app`, затем сделайте **Redeploy**. Проверка: `curl -sI https://yoyo-rent.vercel.app/lv` отвечает `308` с `location: https://yoyo.rent/lv`.
3. **Render.** Сразу после этого впишите тот же `PROXY_SECRET` и замените `WEB_ORIGIN` на `https://yoyo.rent`. Render перезапустит API. Пока этот шаг не сделан, сайт на новом домене получает `403 ORIGIN_FORBIDDEN` на запросы входа.

`PROXY_SECRET` задаётся сначала на Vercel, потом на Render. Наоборот нельзя: API с секретом, но без заголовка от сайта, видит всех посетителей с адресов Vercel, и общие ограничения частоты срабатывают для всех сразу.

> После слияния ветки с аккаунтами проверьте в Render, что у `yoyo-api` появилась переменная `JWT_SECRET`. Её создаёт синхронизация Blueprint. Если деплой упал с `JWT_SECRET: Invalid input`, нажмите в Blueprint `yoyo` **Manual Sync**, затем **Manual Deploy**. Пока новый деплой не прошёл проверку здоровья, Render держит прежнюю версию.

## Аккаунты

Серверная часть аккаунтов: регистрация, подтверждение почты, вход, выход (в том числе со всех устройств), сброс пароля, вход через Google, профиль, смена пароля, удаление аккаунта, подтверждение телефона и роли. Все маршруты лежат под `/api/v1/auth/*`, `/api/v1/me*` и `/api/v1/admin/*` и описаны в Swagger. Экраны входа и настроек появятся в отдельном плане.

### Сессия и cookie

- После входа API ставит две cookie с флагами `HttpOnly` и `SameSite=Lax`, а в production ещё и `Secure`:
  - `yoyo_at`: access-токен на 15 минут, путь `/`;
  - `yoyo_rt`: refresh-токен на 30 дней, путь `/api/v1/auth`.
- Refresh-токен меняется при каждом обновлении сессии. Если старый токен предъявят ещё раз, отзывается вся цепочка: и укравший, и владелец должны войти заново.
- Блокировка и удаление аккаунта действуют сразу: API проверяет пользователя при каждом запросе.
- Конец сессии тоже действует сразу, а не через 15 минут. Access-токен несёт `sid` (цепочку refresh-токенов), и API при каждом запросе проверяет, что у цепочки есть живой refresh-токен. Так работают выход, выход со всех устройств, сброс и смена пароля, повторное предъявление старого refresh-токена и захват неподтверждённого аккаунта через Google.
- `yoyo_dev` — cookie устройства на год, путь `/api/v1/auth`. Её получает браузер после успешного входа или регистрации, она подписана `JWT_SECRET`. Попытки входа с ней считаются по устройству (5 в минуту), а не по email. Поэтому чужие неверные пароли не блокируют владельцу вход с его браузера. Выход эту cookie не удаляет.
- Приложения (позже) работают без cookie: `Authorization: Bearer <access>`, а refresh-токен передают в теле `POST /api/v1/auth/refresh`.

### Один домен для сайта и API

Сайт проксирует `/api/*` на API (`apps/web/src/proxy.ts`; заголовки запроса правилом `rewrites` в `next.config.ts` не добавить, а прокси передаёт API секрет `PROXY_SECRET`). Браузер говорит только с адресом сайта, поэтому cookie остаются cookie самого сайта даже на бесплатных адресах `vercel.app` и `onrender.com`.

- Небезопасные запросы с чужим заголовком `Origin` API отклоняет (`403 ORIGIN_FORBIDDEN`).
- Все ответы API помечены `Cache-Control: no-store`, чтобы CDN Vercel их не кэшировал.
- Из-за двух прокси (Vercel и балансировщик Render) в `render.yaml` задано `TRUST_PROXY_HOPS=2`: так ограничения частоты видят настоящий адрес посетителя.
- Прокси сайта добавляет к каждому запросу заголовок `x-yoyo-proxy-secret` со значением `PROXY_SECRET`. Если `PROXY_SECRET` задан на Render, API верит адресу из `X-Forwarded-For` только при совпадении заголовка (сравнение за постоянное время). Иначе берётся адрес, который видел балансировщик Render. Так прямое обращение к Render не может подделать адрес. Без `PROXY_SECRET` (локально, в тестах) всё работает как раньше. Значение секрета нигде не логируется.
- Ограничения частоты: вход — 5 в минуту на адрес и email, 30 в минуту на адрес по всем email, 20 в час на email; регистрация — 10 в минуту на адрес и `REGISTRATION_HOURLY_CAP` (по умолчанию 100) в час всего.

### Почта

- Локально письма ловит Mailpit (<http://localhost:8025>). Это поведение по умолчанию (`SMTP_URL=smtp://localhost:1025`).
- В production без `SMTP_URL` письма не отправляются. В логе появляется строка `mail disabled` с именем шаблона и замаскированным адресом, но без ссылки. Регистрация и сброс пароля при этом работают, письмо можно запросить повторно.
- **Resend по SMTP.** Бесплатный тариф Render закрывает исходящие порты 25, 465 и 587 ([объявление Render](https://render.com/changelog/free-web-services-will-no-longer-allow-outbound-traffic-to-smtp-ports)), а порт 2465 у Resend работает.
  1. Зарегистрируйтесь на <https://resend.com>, добавьте домен `yoyo.rent` (**Domains → Add Domain**) и впишите у регистратора DNS-записи, которые покажет Resend. Дождитесь статуса Verified.
  2. **API Keys → Create API Key** с правом Sending access.
  3. Впишите в Render `SMTP_URL=smtps://resend:<API_KEY>@smtp.resend.com:2465`, где `<API_KEY>` — ключ `re_…`.
  4. Впишите `MAIL_FROM=Yoyo <no-reply@yoyo.rent>`.
- **Бюджет писем.** Бесплатный Resend отправляет 100 писем в сутки. API отправляет не больше `MAIL_DAILY_LIMIT` (по умолчанию 90) писем за 24 часа. Сверх бюджета письмо пропускается, а в лог раз в час пишется ошибка `daily mail budget … reached`. Запрос пользователя при этом не падает. Писем с подтверждением почты — не больше 5 на аккаунт в сутки (считая письмо при регистрации). Счётчики живут в памяти и обнуляются при перезапуске.

### Телефон

Подтверждение телефона работает только с настоящим SMS-провайдером, чтобы отметка «телефон подтверждён» что-то значила. Такого провайдера пока нет.

- Локально и в тестах `SMS_PROVIDER=mailbox`: код из 6 цифр приходит **письмом** (в Mailpit) и показывает весь сценарий.
- В production `mailbox` запрещён: API с ним не запустится. Без провайдера `POST /api/v1/me/phone*` отвечает `404 AUTH_PROVIDER_DISABLED`, а `GET /api/v1/auth/providers` возвращает `phone: false`.

### Вход через Google

1. Откройте <https://console.cloud.google.com/>, создайте проект и настройте **OAuth consent screen**: тип External, название Yoyo, ваша почта.
2. **APIs & Services → Credentials → Create credentials → OAuth client ID**, тип **Web application**.
3. В **Authorized redirect URIs** добавьте адреса:
   - `https://yoyo.rent/api/v1/auth/google/callback` — адрес сайта, а не API: Google возвращает пользователя через прокси сайта;
   - `https://yoyo-rent.vercel.app/api/v1/auth/google/callback` — старый адрес, нужен до переключения `WEB_ORIGIN` (см. «Свой домен»);
   - `http://localhost:3000/api/v1/auth/google/callback` — для локальной разработки.
4. Скопируйте **Client ID** и **Client secret** в Render (`GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET`) и сохраните. Render перезапустит API.
5. Проверка: `GET https://yoyo.rent/api/v1/auth/providers` возвращает `"google": true`.

Пока ключей нет, вход через Google выключен (`404 AUTH_PROVIDER_DISABLED`), остальное работает.

### Администратор

- Задайте в Render `ADMIN_EMAIL` и `ADMIN_PASSWORD` (не короче 8 символов). При каждом старте API делает этот аккаунт администратором с подтверждённой почтой.
- Если аккаунта нет, API создаёт его с этим паролем. Пароль аккаунта с **подтверждённой** почтой не перезаписывается: после первого входа `ADMIN_PASSWORD` можно удалить.
- Аккаунт с этой почтой, но **без подтверждения**, мог зарегистрировать кто угодно заранее. API забирает его: ставит пароль `ADMIN_PASSWORD`, подтверждает почту и удаляет все его сессии, привязку Google, ссылки и коды (в логе предупреждение с замаскированным адресом).
- Локально то же делает `pnpm --filter @yoyo/api db:seed`.
- Список пользователей для будущей админ-панели: `GET /api/v1/admin/users?search=&page=`.

Секреты (`ADMIN_PASSWORD`, `GOOGLE_CLIENT_SECRET`, `PROXY_SECRET`, ключ внутри `SMTP_URL`, `CLOUDINARY_URL`) вписывает только владелец, в панелях Render и Vercel. В репозиторий они не попадают.

## Объявления

Серверная часть объявлений: категории, черновики, фото, цена, место, календарь, модерация и поиск адреса. Маршруты: `/api/v1/categories`, `/api/v1/listings/*`, `/api/v1/me/listings`, `/api/v1/admin/listings/*`, `/api/v1/geo/*`, `/api/v1/media/*` (описаны в Swagger). Экраны конструктора появятся в плане 6b, каталог и карточка — в плане 7.

### Категории

- Дерево категорий с характеристиками лежит в коде: `apps/api/src/categories/catalog-data.ts`. Названия — на английском, латышском и русском.
- При каждом старте API сверяет базу с этим файлом (`ensureCategories`): добавляет новое и обновляет изменённое. Категорию, которой больше нет в файле, API не удаляет, а выключает (`active=false`). Ручной сид в production не нужен. Два экземпляра API могут стартовать одновременно: сверку по очереди делает блокировка в базе.
- `GET /api/v1/categories` — публичное дерево активных категорий. Ответ можно кэшировать 5 минут.
- Объявление можно отправить на модерацию только в конечной категории (без подкатегорий). Характеристики проверяются по её определениям: лишний ключ, неверный тип или значение не из списка — ошибка по этому полю (`attributes.<key>`).

### Статусы

| Статус | Что значит |
|---|---|
| `DRAFT` | черновик, видит только владелец |
| `PENDING_REVIEW` | на модерации |
| `PUBLISHED` | опубликовано |
| `REJECTED` | отклонено; причину видит владелец |
| `HIDDEN` | скрыто владельцем |
| `ARCHIVED` | удалено, но хранится ради сделок |

Переходы задаёт одна таблица в `apps/api/src/listings/listing-status.ts`:

- черновик или отклонённое → на модерацию (`POST /listings/:id/submit`), если всё заполнено. Иначе `400 LISTING_INCOMPLETE` с полями и шагами конструктора (`details.steps`);
- модерация → опубликовано или отклонено;
- опубликованное ↔ скрытое (`/hide`, `/unhide`);
- правка названия, описания, категории, характеристик, состояния или фото у опубликованного или скрытого объявления возвращает его на модерацию. Так же и правка любого текста, который владелец пишет для всех: своих правил, города и района (иначе после одобрения туда можно было бы вписать что угодно). Правка цены, залога, сроков, готовых правил, точки на карте и дат — нет. Правка, которая делает такое объявление неполным, отклоняется (`400 LISTING_INCOMPLETE`); если неполным его сделала смена каталога, цену, правила и место менять всё равно можно;
- удаление: объявление, которое ни разу не публиковалось (черновик, отклонённое, первая модерация), удаляется вместе с фото; когда-либо опубликованное архивируется. При удалении аккаунта (`DELETE /api/v1/me`) так же поступают со всеми его объявлениями, а у архивных стирается точка на карте;
- с архивным объявлением ничего сделать нельзя (`409 INVALID_STATUS`).

Чужое объявление для пользователя не существует: на любые действия с ним API отвечает `404`. Администратор видит все объявления. Точную точку (`lat`, `lng`) видят только владелец и администратор, остальным показывается район.

`PATCH /listings/:id` принимает любые поля черновика и обязательный `version` — версию, которую клиент видел последней. Если объявление тем временем изменили (другая вкладка), ответ `409 INVALID_STATUS` с `details.currentVersion`. Ответы на загрузку и перестановку фото и на изменение дат тоже содержат новую `version`; перестановка фото и даты принимают необязательный `version` с той же проверкой. Те же даты ещё раз ничего не меняют.

Цены, скидки, залог и сроки проверяет ядро `@yoyo/domain` (`validatePricing`), даты недоступности — его же `period()`. Пересекающиеся и соседние периоды склеиваются, прошедшие отбрасываются (по часовому поясу объявления). Весь текст пользователя очищается от HTML.

### Фото

- До 8 фото на объявление, до 10 МБ каждое, только JPEG, PNG и WebP. Тип определяется по первым байтам файла, а не по `Content-Type` и имени: HTML, SVG и остальное получают `415 UNSUPPORTED_MEDIA`, файл больше 10 МБ или больше 50 мегапикселей — `413 PAYLOAD_TOO_LARGE`, девятое фото — `409 PHOTO_LIMIT`.
- Сервер поворачивает фото по EXIF, уменьшает длинную сторону до 2048 px и перекодирует в WebP. При этом удаляются все метаданные, в том числе GPS-координаты из EXIF. Оригинал нигде не сохраняется.
- Файлы хранятся под случайными ключами, имя файла пользователя нигде не используется. Первое по порядку фото — обложка. Порядок меняет `PUT /listings/:id/photos/order` со списком всех фото.
- В ответах три адреса: `thumb` 160×120, `card` 640×480 (обрезка по центру) и `full` до 2048 px.
- **Хранилище** задаёт `STORAGE`:
  - `local` — папка `apps/api/.uploads` (в git не попадает), по умолчанию в разработке и тестах. Файлы отдаёт сам API: `/api/v1/media/<key>/<thumb|card|full>`. В production `local` запрещён: диск Render стирается при каждом деплое;
  - `cloudinary` — бесплатный тариф Cloudinary, задан в `render.yaml`. Нужен `CLOUDINARY_URL`.
- Пока хранилища нет, API работает, а загрузка фото отвечает `503 STORAGE_DISABLED`.

**Как подключить Cloudinary (владелец, один раз):**

1. Зарегистрироваться на <https://cloudinary.com> (бесплатно, без карты).
2. Console → **Settings → API Keys**: скопировать строку `CLOUDINARY_URL=cloudinary://<api_key>:<api_secret>@<cloud_name>`.
3. Render → `yoyo-api` → **Environment**: вставить значение (без `CLOUDINARY_URL=`) в `CLOUDINARY_URL`, сохранить. Render перезапустит API.

API отправляет фото на Cloudinary уже очищенными от метаданных, с подписью каждого запроса (SHA-1 с секретом) и без SDK. Фото лежат в папке `yoyo/listings`. Если аккаунт Cloudinary сохранит фото под другим `public_id` (режим папок не тот), API отменит загрузку, ответит `503` и напишет в лог, что проверить.

### Модерация

- `GET /api/v1/admin/listings?status=PENDING_REVIEW&page=` — очередь, старые первыми, по 20 на странице.
- `POST /api/v1/admin/listings/:id/approve` публикует объявление. `POST /api/v1/admin/listings/:id/reject` с `{ "reason": "…" }` (10–500 символов) отклоняет. Обязательный `version` в теле — версия, которую видел администратор: если владелец успел изменить объявление, ответ `409 INVALID_STATUS`, и непросмотренное не публикуется.
- Решать можно только объявление на модерации (`409 INVALID_STATUS`). Обычный пользователь получает `403`. Свои объявления администратор не модерирует.
- Владелец получает письмо на своём языке: об одобрении — со ссылкой на объявление, об отказе — с причиной и ссылкой на правку. Письма идут через общий дневной бюджет `MAIL_DAILY_LIMIT`.

### Поиск адреса

- `GET /api/v1/geo/search?q=&lang=` (до 5 мест с городом, районом и точкой) и `GET /api/v1/geo/reverse?lat=&lng=&lang=` (город и район точки). Нужен вход, 30 запросов в минуту на пользователя.
- Геокодер — Nominatim (OpenStreetMap), адрес задаёт `NOMINATIM_URL`. API соблюдает его правила: не больше 1 запроса в секунду со всего сервера (остальные ждут в очереди до 5 секунд, потом `503 GEO_UNAVAILABLE`), заголовок `User-Agent: Yoyo/1.0 (+https://yoyo.rent)`, ответы хранятся в базе 30 дней, и одинаковый запрос не уходит к Nominatim дважды.
- В каждом ответе есть `attribution` («© OpenStreetMap contributors»). Сайт обязан показывать эту подпись рядом с картой и результатами поиска.

## Сделки и кошелёк

Серверная часть сделки на ядре `@yoyo/domain`: цена, предложение своей цены, бронь, договор, оплата, передача, возврат, залог, отмены, споры, сроки и кошелёк. Маршруты: `/api/v1/listings/:id/quote`, `/api/v1/listings/:id/offers`, `/api/v1/offers/*`, `/api/v1/bookings/*`, `/api/v1/me/bookings`, `/api/v1/me/offers`, `/api/v1/wallet/*`, `/api/v1/payments/card-tokens`, `/api/v1/admin/bookings/*`, `/api/v1/admin/ledger/*` (описаны в Swagger). Экраны — отдельный план. План: [`docs/superpowers/plans/2026-11-05-yoyo-08-deals-api.md`](docs/superpowers/plans/2026-11-05-yoyo-08-deals-api.md).

### Как устроена сделка

- Правила (статусы, кто что может, сроки, деньги) живут только в ядре: таблица переходов и пример с деньгами — в [`packages/domain/README.md`](packages/domain/README.md). API загружает сделку, блокирует строку, спрашивает ядро и в одной транзакции сохраняет ответ, журнал событий (`BookingEvent`) и эффекты: проводки, занятые даты, договор, письма.
- Каждый шаг — `POST /api/v1/bookings/:id/events` с `{ "version": n, "event": { "type": "ACCEPT" } }`. `version` — та, что клиент видел последней: если сделка тем временем изменилась, ответ `409 INVALID_STATUS` с `details.currentVersion`. Какие кнопки показать, говорит `actions` в ответе (`availableActions` ядра).
- Если срок прошёл раньше, чем сторона нажала кнопку, побеждает срок: API выполняет таймер, а шаг получает `409 DEADLINE_PASSED` с новым статусом.
- Сделку видят только её стороны и администратор, для остальных её нет (`404`).
- На вещь заблокированного или удалённого владельца нельзя отправить запрос или предложение цены, его бронь нельзя оплатить (`409 LISTING_UNAVAILABLE`).
- **Двойная бронь невозможна в самой базе.** Когда владелец принимает запрос, дни сделки записываются в колонку `reserved` (`daterange`), а ограничение-исключение `Booking_no_double_booking` (`btree_gist`) не даёт двум сделкам одной вещи занять общий день. Гонку двух одновременных «Принять» ловит база: проигравший получает `409 DATES_UNAVAILABLE`.

### Деньги

- Все суммы — целые центы EUR. Каждое движение денег — операция журнала (`LedgerOperation` и её проводки `LedgerEntry`), сумма проводок всегда 0. Баланс счёта (`LedgerAccount`) — кэш суммы его проводок, обновляется в той же транзакции.
- База сама следит за деньгами: проводки нельзя изменить или удалить (триггер), несбалансированная операция не проходит коммит (отложенный триггер), кошелёк, escrow и залог не уходят ниже нуля (`CHECK`).
- `GET /api/v1/admin/ledger/summary` показывает итоги по счетам и проверку всего журнала (`audit`: сумма 0, кэш совпадает, нет несбалансированных операций и отрицательных балансов).
- Свойство (fast-check) прогоняет случайные сделки через настоящую базу и после каждого шага проверяет то же самое: `apps/api/test/ledger.property.e2e.test.ts`. `FC_RUNS` и `FC_SEED` меняют число прогонов и сид.

### Оплата (имитация)

Оплата идёт через интерфейс `PaymentProvider` (`apps/api/src/payments/payment.provider.ts`). Сейчас там тестовая карта (`PAYMENTS=fake`): она проверяет номер, срок и CVC как настоящая форма, но настоящие деньги не двигаются. Номер карты не хранится и не попадает в лог: `POST /api/v1/payments/card-tokens` превращает его в токен на 15 минут, в базе остаются марка и последние 4 цифры. Позже сюда подключается Stripe Connect — новым классом за тем же интерфейсом.

| Номер | Результат |
|---|---|
| `4242 4242 4242 4242`, `5555 5555 5555 4444` | оплата проходит |
| `4000 0000 0000 0002` | `402 PAYMENT_DECLINED`, `card_declined` |
| `4000 0000 0000 9995` | `insufficient_funds` |
| `4000 0000 0000 0069` | `expired_card` |
| `4000 0000 0000 0119` | `processing_error` |

Срок — любой будущий месяц, CVC — 3 цифры (у American Express 4).

- **Ключ идемпотентности.** Запросы, которые двигают деньги (`POST /bookings/:id/events`, `/wallet/top-ups`, `/wallet/payouts`, `/admin/bookings/:id/resolve`), требуют заголовок `Idempotency-Key` (8–100 символов `A–Z a–z 0–9 - _`), новый на каждое действие пользователя. Повтор с тем же ключом и телом получает первый ответ (`Idempotent-Replayed: true`) и ничего не списывает второй раз. Ключи живут сутки.
- Карту списывают до транзакции, после пробного решения ядра; если сделка не приняла оплату, деньги сразу возвращаются. Возвраты на карту и выплаты записываются в той же транзакции, что и проводки, и уходят провайдеру после неё. Невыполненное повторяет задача сроков.
- Деньги возвращаются тем же способом, которым платили: картой — на карту, из кошелька — в кошелёк.

### Кошелёк

- `GET /api/v1/wallet` — баланс и сколько держат открытые сделки; `GET /api/v1/wallet/transactions` — история со ссылками на сделки.
- `POST /api/v1/wallet/top-ups` — пополнение картой: от 1 € до 500 € за раз, в кошельке не больше 5000 €. `POST /api/v1/wallet/payouts` — вывод на карту. По 10 в час.

### Договор

При «Принять» условия договора замораживаются (стороны, вещь, правила, даты, цена, сроки) вместе с их SHA-256. `GET /api/v1/bookings/:id/contract.pdf?lang=en|lv|ru` рисует PDF на нужном языке (по умолчанию — на языке зрителя) со шрифтом Liberation Sans (SIL OFL 1.1, `apps/api/assets/fonts`), который знает латышские буквы и кириллицу. Подписи — кнопка «Подписать» в сделке; время подписи печатается в договоре.

### Письма

Каждое событие сделки, о котором ядро говорит «уведомить», и каждый шаг предложения цены — письмо получателю на его языке, после коммита, через общий бюджет `MAIL_DAILY_LIMIT`. О новом споре пишут администраторам (до 5). Тексты — `apps/api/src/mail/i18n/*.json`, раздел `deal`; тест обходит пути сделки в ядре и проверяет, что у каждого письма есть текст на трёх языках.

### Сроки

Бесплатный сервер Render засыпает, поэтому в памяти никаких таймеров нет. Срок сделки хранится в строке (`timerDueAt`), а просроченные выполняет `TimersService.runDue()`:

- при каждом старте API (в фоне);
- по `POST /api/v1/internal/timers/run` с заголовком `Authorization: Bearer <TIMERS_SECRET>`. Его каждые 10 минут вызывает GitHub Actions (`.github/workflows/timers.yml`); заодно это будит сервер.

Запуск безопасен поздно, дважды и одновременно: сделки берутся по одной (`FOR UPDATE SKIP LOCKED`), а ядро игнорирует таймер, который не взведён или ещё не наступил. Тот же запуск закрывает истекшие предложения цены, досылает возвраты и выплаты и забывает ключи идемпотентности старше суток. Без `TIMERS_SECRET` маршрута нет (`404`).

**Как включить расписание (владелец, один раз):**

1. Render → `yoyo-api` → **Environment**: после деплоя там появится `TIMERS_SECRET` (его генерирует Blueprint). Скопировать значение. Если переменной нет — Blueprint `yoyo` → **Manual Sync**.
2. GitHub → репозиторий → **Settings → Secrets and variables → Actions → New repository secret**:
   - `TIMERS_SECRET` — скопированное значение;
   - `API_URL` — `https://yoyo-api.onrender.com`.
3. **Actions → Run due timers → Run workflow**: задача должна закончиться зелёной, в логе — ответ с `"fired"`.

GitHub запускает расписание только из ветки `main` и может опаздывать на несколько минут; сроки сделки от этого не сдвигаются: просроченный срок всё равно побеждает опоздавшую кнопку. Запрос раз в 10 минут не даёт серверу уснуть и расходует часы бесплатного тарифа Render: 750 часов в месяц хватает одному сервису на весь месяц.

### Споры

`GET /api/v1/admin/bookings?disputed=true` — очередь споров, старые первыми. `GET /api/v1/admin/bookings/:id` — сделка с журналом, проводками, оплатами и фото. `POST /api/v1/admin/bookings/:id/resolve` с `{ "version", "decision", "comment" }`: `REFUND_DEPOSIT` или `DEPOSIT_TO_OWNER` для повреждения и невозврата, `REFUND_ALL` или `CONFIRM_HANDOVER`, если вещь не передали. Свои сделки администратор не решает. Фото состояния при передаче, возврате и повреждения стороны загружают в `POST /api/v1/bookings/:id/photos?kind=HANDOVER|RETURN|DAMAGE`.
